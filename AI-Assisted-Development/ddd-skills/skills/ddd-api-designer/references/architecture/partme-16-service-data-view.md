ในสถาปัตยกรรมแบบแบ่งชั้น DDD และโมเดลโค้ดไมโครเซอร์วิส เราแบ่งชั้นออบเจ็กต์โดเมนตามคุณสมบัติและความสัมพันธ์เชิงพึ่งพาของออบเจ็กต์โดเมน และกำหนดออบเจ็กต์โค้ดและโครงสร้างไดเรกทอรีโค้ดที่สอดคล้องกัน สถาปัตยกรรมแบบแบ่งชั้นกำหนดสถาปัตยกรรมโดยรวมของไมโครเซอร์วิส ออบเจ็กต์หลักภายในไมโครเซอร์วิสได้แก่บริการและเอนทิตี เป็นต้น ซึ่งทำงานร่วมกันเพื่อให้ logic ธุรกิจสำเร็จ

แล้วในระหว่างการทำงาน บริการและเอนทิตีเหล่านี้ทำงานร่วมกันในแต่ละชั้นของไมโครเซอร์วิสอย่างไร? วันนี้เรามาชำแหละไมโครเซอร์วิสที่อิงตามสถาปัตยกรรมแบบแบ่งชั้น DDD กัน ดูว่าโครงสร้างภายในเป็นอย่างไร

1. ประเภทของบริการ

ก่อนอื่นเรามาทบทวนบริการในสถาปัตยกรรมแบบแบ่งชั้นกันก่อน ไมโครเซอร์วิสที่ออกแบบตามสถาปัตยกรรมแบบแบ่งชั้น ภายในมีบริการ Facade, บริการแอปพลิเคชัน, บริการโดเมน และบริการพื้นฐาน หน้าที่และความรับผิดชอบหลักของบริการแต่ละชั้นมีดังนี้

บริการ Facade:

ตั้งอยู่ที่ชั้นอินเทอร์เฟซผู้ใช้ ประกอบด้วยอินเทอร์เฟซและการนำไปใช้ ใช้สำหรับจัดการคำขอ Restful ที่ผู้ใช้ส่งมาและแยกวิเคราะห์ไฟล์กำหนดค่าที่ผู้ใช้ป้อน เป็นต้น และส่งข้อมูลต่อไปยังชั้นแอปพลิเคชัน หรือหลังจากได้รับข้อมูลจากชั้นแอปพลิเคชันแล้ว ประกอบ DO เป็น DTO และส่งข้อมูลไปยังแอปพลิเคชันส่วนหน้า

ตั้งอยู่ที่ชั้นแอปพลิเคชัน ใช้เพื่อแสดงพฤติกรรมของแอปพลิเคชันและผู้ใช้ รับผิดชอบการรวม การเรียบเรียง และการส่งต่อบริการ รับผิดชอบจัดการลำดับการทำงานของกรณีใช้งานทางธุรกิจและการประกอบผลลัพธ์ ให้บริการแบบ coarse-grained แก่ภายนอก

ตั้งอยู่ที่ชั้นโดเมน บริการโดเมนห่อหุ้ม logic ธุรกิจหลัก ทำให้ logic โดเมนหลักที่ต้องใช้เอนทิตีหลายตัวทำงานร่วมกันสำเร็จ มันรวมหรือเรียบเรียง logic ธุรกิจของเอนทิตีหรือเมธอดหลายตัว หรือในสถาปัตยกรรมแบบแบ่งชั้นอย่างเข้มงวด จะห่อหุ้มเมธอดของเอนทิตีในรูปแบบของบริการโดเมนเพื่อให้ชั้นแอปพลิเคชันเรียกใช้

ตั้งอยู่ที่ชั้นพื้นฐาน ให้บริการทรัพยากรพื้นฐาน (เช่น ฐานข้อมูล แคช เป็นต้น) ทำให้แต่ละชั้นลดการเชื่อมโยงกัน ลดผลกระทบจากการเปลี่ยนแปลงทรัพยากรภายนอกต่อ logic แอปพลิเคชันธุรกิจ บริการพื้นฐานส่วนใหญ่เป็นบริการที่เก็บข้อมูล (Repository) ให้บริการทรัพยากรพื้นฐานผ่านการกลับทิศทางการพึ่งพา บริการโดเมนและบริการแอปพลิเคชันสามารถเรียกใช้อินเทอร์เฟซบริการที่เก็บข้อมูลได้ และทำให้ข้อมูลคงอยู่ถาวรผ่านบริการที่เก็บข้อมูล

2. การเรียกใช้บริการ

เรามาดูภาพด้านล่าง การเรียกใช้บริการของไมโครเซอร์วิสประกอบด้วยสามสถานการณ์หลัก: การเรียกใช้บริการข้ามชั้นภายในไมโครเซอร์วิส, การเรียกใช้บริการระหว่างไมโครเซอร์วิส และการขับเคลื่อนด้วยเหตุการณ์โดเมน

การเรียกใช้บริการข้ามชั้นภายในไมโครเซอร์วิส

ภายใต้สถาปัตยกรรมไมโครเซอร์วิสมักใช้รูปแบบการออกแบบแยกส่วนหน้าและส่วนหลัง โดยแอปพลิเคชันส่วนหน้าปรับใช้แยกกัน แอปพลิเคชันส่วนหน้าเรียกใช้บริการ Facade ที่เผยแพร่บน API Gateway และ Facade ส่งต่อไปยังบริการแอปพลิเคชัน บริการแอปพลิเคชันในฐานะผู้จัดระเบียบและเรียบเรียงบริการ มีเส้นทางการเรียกใช้บริการสองแบบ:

แบบแรกคือ บริการแอปพลิเคชันเรียกใช้และประกอบบริการโดเมน ในกรณีนี้บริการโดเมนจะประกอบเอนทิตีและเมธอดของเอนทิตี ทำให้ logic โดเมนหลักสำเร็จ บริการโดเมนได้รับออบเจ็กต์ข้อมูลที่คงอยู่ถาวรผ่านบริการที่เก็บข้อมูล เพื่อทำการเริ่มต้นข้อมูลเอนทิตีให้สมบูรณ์

แบบที่สองคือ บริการแอปพลิเคชันเรียกใช้บริการที่เก็บข้อมูลโดยตรง วิธีนี้ส่วนใหญ่ใช้กับข้อมูลประเภทพื้นฐานเช่นแคช ไฟล์ เป็นต้น ข้อมูลประเภทนี้ส่วนใหญ่เป็นการดำเนินการค้นหา ไม่มี logic โดเมนมากนัก ไม่ผ่านชั้นโดเมน ไม่เกี่ยวข้องกับออบเจ็กต์การคงอยู่ถาวรของฐานข้อมูล

การเรียกใช้บริการระหว่างไมโครเซอร์วิส

บริการแอปพลิเคชันระหว่างไมโครเซอร์วิสสามารถเข้าถึงได้โดยตรง หรือเข้าถึงผ่าน API Gateway เนื่องจากเป็นการดำเนินการข้ามไมโครเซอร์วิส เมื่อทำการเพิ่มและแก้ไขข้อมูล คุณต้องให้ความสำคัญกับธุรกรรมแบบกระจาย เพื่อรับประกันความสอดคล้องของข้อมูล

การขับเคลื่อนด้วยเหตุการณ์โดเมน

การขับเคลื่อนด้วยเหตุการณ์โดเมนประกอบด้วยเหตุการณ์ภายในไมโครเซอร์วิสและระหว่างไมโครเซอร์วิส (ดูรายละเอียด) ภายในไมโครเซอร์วิสทำการประมวลผลแบบอะซิงโครนัสระหว่าง aggregate ผ่าน EventBus ระหว่างไมโครเซอร์วิสทำผ่าน middleware ข้อความ กลไกการขับเคลื่อนด้วยเหตุการณ์โดเมนแบบอะซิงโครนัสเป็นวิธีการเข้าถึงบริการทางอ้อม

เมื่อ logic ธุรกิจของบริการแอปพลิเคชันประมวลผลเสร็จ หากมีเหตุการณ์โดเมนเกิดขึ้น สามารถเรียกใช้บริการเผยแพร่เหตุการณ์เพื่อเผยแพร่เหตุการณ์ได้

เมื่อได้รับข้อมูลหัวข้อที่สมัครรับ บริการสมัครรับเหตุการณ์จะเรียกใช้บริการโดเมนจัดการเหตุการณ์ เพื่อดำเนินการทางธุรกิจต่อไป

3. การห่อหุ้มและการรวมบริการ

เรามาดูภาพด้านล่าง บริการของไมโครเซอร์วิสถูกห่อหุ้ม รวม และเปิดเผยจากชั้นโดเมนขึ้นไปทีละชั้น

รูปแบบบริการของชั้นพื้นฐานส่วนใหญ่คือบริการที่เก็บข้อมูล บริการที่เก็บข้อมูลประกอบด้วยอินเทอร์เฟซและการนำไปใช้ อินเทอร์เฟซบริการที่เก็บข้อมูลให้บริการสำหรับการเรียกใช้ของชั้นแอปพลิเคชันหรือชั้นโดเมน การนำไปใช้บริการที่เก็บข้อมูลทำให้ออบเจ็กต์โดเมนคงอยู่ถาวรหรือเริ่มต้นข้อมูล

ชั้นโดเมนทำให้ logic ธุรกิจหลักสำเร็จ รับผิดชอบแสดงแนวคิดทางธุรกิจของโดเมนโมเดล สถานะทางธุรกิจ และกฎทางธุรกิจ รูปแบบบริการหลักได้แก่เมธอดของเอนทิตีและบริการโดเมน

เอนทิตีใช้โมเดลแบบ rich model ภายในคลาสเอนทิตีทำให้ logic ธุรกิจทั้งหมดที่เกี่ยวข้องกับเอนทิตีสำเร็จ รูปแบบการทำให้สำเร็จคือเมธอดในคลาสเอนทิตี เอนทิตีเป็นหน่วย logic ธุรกิจระดับอะตอมของไมโครเซอร์วิส ในการออกแบบเราให้ความสำคัญกับคุณสมบัติและพฤติกรรมทางธุรกิจของเอนทิตีเองเป็นหลัก ทำให้ความสามารถพื้นฐานหลักของโดเมนโมเดลสำเร็จ ไม่จำเป็นต้องคำนึงถึงการดำเนินการภายนอกและกระบวนการทางธุรกิจมากเกินไป ด้วยวิธีนี้จึงสามารถรับประกันความเสถียรของโดเมนโมเดลได้

DDD สนับสนุน rich domain model พยายามกำหนด logic ธุรกิจให้กับออบเจ็กต์เอนทิตีให้มากที่สุด ส่วนที่กำหนดไม่ได้จริงๆ ก็ออกแบบเป็นบริการโดเมน บริการโดเมนจะประกอบและเรียบเรียงเอนทิตีหรือเมธอดของเอนทิตีหลายตัว ทำให้ logic ธุรกิจหลักที่ซับซ้อนซึ่งข้ามเอนทิตีหลายตัวสำเร็จ

สำหรับสถาปัตยกรรมแบบแบ่งชั้นอย่างเข้มงวด หากเมธอดของเอนทิตีเดียวต้องเปิดเผยต่อชั้นแอปพลิเคชัน จำเป็นต้องห่อหุ้มผ่านบริการโดเมนก่อนจึงจะเปิดเผยต่อบริการแอปพลิเคชันได้

ชั้นแอปพลิเคชันใช้เพื่อแสดงพฤติกรรมของแอปพลิเคชันและผู้ใช้ รับผิดชอบการรวม การเรียบเรียง และการส่งต่อบริการ รับผิดชอบจัดการลำดับการทำงานของกรณีใช้งานทางธุรกิจและการประกอบผลลัพธ์ รับผิดชอบการประสานงานบริการและข้อมูลระหว่าง aggregate ต่างๆ รับผิดชอบการเผยแพร่และสมัครรับเหตุการณ์ระหว่างไมโครเซอร์วิส

ผ่านบริการแอปพลิเคชันเปิดเผยฟังก์ชันภายในของไมโครเซอร์วิสต่อภายนอก ด้วยวิธีนี้จึงสามารถซ่อนความซับซ้อนของ logic ธุรกิจหลักของชั้นโดเมนและกลไกการนำไปใช้ภายในได้ รูปแบบบริการหลักของชั้นแอปพลิเคชันได้แก่: บริการแอปพลิเคชัน, บริการเผยแพร่และสมัครรับเหตุการณ์

บริการที่ใช้สำหรับการรวมและเรียบเรียงภายในบริการแอปพลิเคชัน ส่วนใหญ่มาจากบริการโดเมน หรืออาจเป็นบริการแอปพลิเคชันของไมโครเซอร์วิสภายนอกก็ได้ นอกจากการรวมและเรียบเรียงบริการแล้ว ภายในบริการแอปพลิเคชันยังสามารถทำงานเช่นการยืนยันตัวตน การตรวจสอบสิทธิ์ การตรวจสอบข้อมูลเบื้องต้น และการควบคุมธุรกรรมแบบกระจายได้

เพื่อให้เกิดการลดการเชื่อมโยงระหว่าง aggregate ภายในไมโครเซอร์วิส การเรียกใช้บริการและการแลกเปลี่ยนข้อมูลระหว่าง aggregate ควรทำผ่านบริการแอปพลิเคชัน ตามหลักการแล้วเราควรห้ามการเรียกใช้บริการโดเมนโดยตรงระหว่าง aggregate และการเชื่อมตารางข้อมูลระหว่าง aggregate

ชั้นอินเทอร์เฟซผู้ใช้เป็นสะพานเชื่อมระหว่างการเข้าถึงบริการและการแลกเปลี่ยนข้อมูลระหว่างแอปพลิเคชันส่วนหน้ากับไมโครเซอร์วิส มันจัดการคำขอ Restful ที่ส่วนหน้าส่งมาและแยกวิเคราะห์ไฟล์กำหนดค่าที่ผู้ใช้ป้อน เป็นต้น ส่งข้อมูลต่อไปยังชั้นแอปพลิเคชัน หรือหลังจากได้รับข้อมูลจากบริการแอปพลิเคชันแล้ว ทำการประกอบข้อมูล ให้บริการข้อมูลแก่ส่วนหน้า รูปแบบบริการหลักคือบริการ Facade

บริการ Facade แบ่งเป็นสองส่วนคืออินเทอร์เฟซและการนำไปใช้ ทำให้การส่งต่อบริการเสร็จสมบูรณ์ การแปลงและประกอบข้อมูล DO กับ DTO ทำให้การแปลงและแลกเปลี่ยนข้อมูลระหว่างส่วนหน้ากับชั้นแอปพลิเคชันสำเร็จ

4. ความสัมพันธ์เชิงพึ่งพาของบริการในสถาปัตยกรรมแบบแบ่งชั้นสองแบบ

ตอนนี้เรามาทบทวนสถาปัตยกรรมแบบแบ่งชั้น DDD กัน สถาปัตยกรรมแบบแบ่งชั้นมีหลักการสำคัญประการหนึ่งคือ: แต่ละชั้นสามารถเชื่อมโยงกับชั้นที่อยู่ด้านล่างได้เท่านั้น

ตามระดับความแน่นของการเชื่อมโยง สถาปัตยกรรมแบบแบ่งชั้นสามารถแบ่งได้เป็นสองแบบ: สถาปัตยกรรมแบบแบ่งชั้นอย่างเข้มงวดและสถาปัตยกรรมแบบแบ่งชั้นแบบหลวม ในสถาปัตยกรรมแบบแบ่งชั้นอย่างเข้มงวด ชั้นใดๆ สามารถพึ่งพาได้เฉพาะชั้นที่อยู่ด้านล่างโดยตรงเท่านั้น ในสถาปัตยกรรมแบบแบ่งชั้นแบบหลวม ชั้นใดๆ สามารถพึ่งพาชั้นใดก็ได้ที่อยู่ด้านล่าง

ต่อไปเรามาวิเคราะห์และเปรียบเทียบสถาปัตยกรรมแบบแบ่งชั้นสองแบบนี้อย่างละเอียด

ความสัมพันธ์เชิงพึ่งพาของบริการในสถาปัตยกรรมแบบแบ่งชั้นแบบหลวม

เรามาดูภาพด้านล่าง ในสถาปัตยกรรมแบบแบ่งชั้นแบบหลวม เมธอดของเอนทิตีและบริการโดเมนในชั้นโดเมนสามารถเปิดเผยต่อชั้นแอปพลิเคชันและชั้นอินเทอร์เฟซผู้ใช้ได้โดยตรง ความสัมพันธ์เชิงพึ่งพาของบริการในสถาปัตยกรรมแบบแบ่งชั้นแบบหลวม ไม่จำเป็นต้องห่อหุ้มทีละชั้น สามารถเปิดเผยต่อชั้นบนได้อย่างรวดเร็ว

แต่มีปัญหาบางประการ ประการแรกคือเปิดเผย logic การนำไปใช้ของธุรกิจหลักในชั้นโดเมนได้ง่าย ประการที่สองเมื่อเมธอดของเอนทิตีหรือบริการโดเมนเกิดการเปลี่ยนแปลงบริการ เนื่องจากบริการถูกเรียกใช้และรวมโดยหลายชั้นพร้อมกัน จึงไม่ใช่เรื่องง่ายที่จะหาว่าบริการชั้นบนใดเรียกใช้และรวมมันไว้ ไม่สะดวกในการแจ้งไปยังผู้เรียกใช้บริการทั้งหมด

เรามาดูอีกภาพหนึ่ง ในสถาปัตยกรรมแบบแบ่งชั้นแบบหลวม หลังจากเมธอดของเอนทิตี A ถูกประกอบในชั้นแอปพลิเคชันแล้ว เปิดเผยต่อ aFacade ของชั้นอินเทอร์เฟซผู้ใช้ บริการโดเมน abDomainService ข้ามชั้นแอปพลิเคชันโดยตรง เปิดเผยต่อบริการ abFacade ของชั้นอินเทอร์เฟซผู้ใช้ ในสถาปัตยกรรมแบบแบ่งชั้นแบบหลวม บริการชั้นล่างใดๆ สามารถเปิดเผยต่อบริการชั้นบนได้

ความสัมพันธ์เชิงพึ่งพาของบริการในสถาปัตยกรรมแบบแบ่งชั้นอย่างเข้มงวด

เรามาดูภาพด้านล่าง ในสถาปัตยกรรมแบบแบ่งชั้นอย่างเข้มงวด บริการแต่ละชั้นสามารถให้บริการได้เฉพาะชั้นบนที่อยู่ติดกันเท่านั้น แม้ว่าเอนทิตี เมธอดของเอนทิตี และบริการโดเมนจะอยู่ในชั้นโดเมน แต่เอนทิตีและเมธอดของเอนทิตีสามารถเปิดเผยต่อบริการโดเมนได้เท่านั้น และบริการโดเมนสามารถเปิดเผยต่อบริการแอปพลิเคชันได้เท่านั้น

ในสถาปัตยกรรมแบบแบ่งชั้นอย่างเข้มงวด หากบริการต้องการเรียกใช้ข้ามชั้น บริการชั้นล่างจำเป็นต้องห่อหุ้มในชั้นบนก่อนจึงจะสามารถให้บริการข้ามชั้นได้ ตัวอย่างเช่น หากเมธอดของเอนทิตีต้องการให้บริการแก่บริการแอปพลิเคชัน จำเป็นต้องห่อหุ้มเป็นบริการโดเมน

เนื่องจากผ่านการห่อหุ้มคุณสามารถหลีกเลี่ยงการเปิดเผยการนำไปใช้ของ logic ธุรกิจหลักต่อภายนอกได้ การห่อหุ้มเอนทิตีและเมธอดเป็นบริการโดเมนยังสามารถหลีกเลี่ยงการสะสม logic ธุรกิจหลักที่ควรอยู่ในชั้นโดเมนมากเกินไปในชั้นแอปพลิเคชัน หลีกเลี่ยงความอ้วนของชั้นแอปพลิเคชัน นอกจากนี้เมื่อบริการเกิดการเปลี่ยนแปลง เนื่องจากบริการถูกเรียกใช้และรวมโดยบริการชั้นบนที่อยู่ติดกันเท่านั้น คุณเพียงแค่แจ้งชั้นบนที่อยู่ติดกันทีละชั้นก็เพียงพอ ความสามารถในการจัดการบริการจึงดีกว่าสถาปัตยกรรมแบบแบ่งชั้นแบบหลวมอย่างแน่นอน

เรายังดูภาพเดิม เมธอดของเอนทิตี A ต้องห่อหุ้มเป็นบริการโดเมน aDomainService จึงจะเปิดเผยต่อบริการแอปพลิเคชัน aAppService ได้ บริการโดเมน abDomainService หลังจากรวมและห่อหุ้มเมธอดของเอนทิตี A และ B แล้ว เปิดเผยต่อบริการแอปพลิเคชัน abAppService

มุมมองออบเจ็กต์ข้อมูล

ใน DDD มีออบเจ็กต์ข้อมูลหลายชนิด ออบเจ็กต์เหล่านี้กระจายอยู่ในชั้นต่างๆ ในแต่ละช่วงเวลามีรูปแบบที่แตกต่างกัน คุณสามารถทบทวนได้อีกครั้ง การบรรยายนี้มีคำอธิบายโดยละเอียด

ก่อนอื่นเรามาดูว่าภายในไมโครเซอร์วิสมีออบเจ็กต์ข้อมูลประเภทใดบ้าง? พวกมันทำงานร่วมกันและแปลงอย่างไร?

ออบเจ็กต์การคงอยู่ถาวร PO (Persistent Object) แมปกับโครงสร้างฐานข้อมูลแบบหนึ่งต่อหนึ่ง เป็นตัวพาข้อมูลในกระบวนการคงอยู่ถาวรของข้อมูล

ออบเจ็กต์โดเมน DO (Domain Object) เอนทิตีขณะรันของไมโครเซอร์วิส เป็นตัวพาของธุรกิจหลัก

ออบเจ็กต์ถ่ายโอนข้อมูล DTO (Data Transfer Object) ใช้สำหรับการประกอบและถ่ายโอนข้อมูลระหว่างส่วนหน้ากับชั้นแอปพลิเคชันหรือระหว่างไมโครเซอร์วิส เป็นตัวพาการถ่ายโอนข้อมูลระหว่างแอปพลิเคชัน

ออบเจ็กต์มุมมอง VO (View Object) ใช้สำหรับห่อหุ้มข้อมูลของหน้าเพจหรือคอมโพเนนต์ที่ระบุในชั้นแสดงผล

เรามาดูภาพด้านล่างร่วมกัน เพื่อดูหน้าที่และกระบวนการแปลงของออบเจ็กต์ข้อมูลในแต่ละชั้นของไมโครเซอร์วิส

ออบเจ็กต์หลักของชั้นพื้นฐานคือออบเจ็กต์ PO เราจำเป็นต้องสร้างความสัมพันธ์การแมประหว่าง DO และ PO ก่อน เมื่อข้อมูล DO ต้องการคงอยู่ถาวร บริการที่เก็บข้อมูลจะแปลง DO เป็นออบเจ็กต์ PO ทำให้การคงอยู่ถาวรของฐานข้อมูลสำเร็จ เมื่อข้อมูล DO ต้องการเริ่มต้น บริการที่เก็บข้อมูลจะได้รับข้อมูลจากฐานข้อมูลเป็นออบเจ็กต์ PO และแปลง PO เป็น DO ทำให้การเริ่มต้นข้อมูลสำเร็จ

ในกรณีส่วนใหญ่ PO และ DO มีความสัมพันธ์แบบหนึ่งต่อหนึ่ง แต่ก็มีกรณีที่ DO และ PO มีความสัมพันธ์แบบหลายต่อหลาย ในการแปลงข้อมูลระหว่าง DO และ PO จำเป็นต้องทำการประกอบข้อมูลใหม่

ออบเจ็กต์หลักของชั้นโดเมนคือออบเจ็กต์ DO DO เป็นตัวพาข้อมูลและพฤติกรรมทางธุรกิจของเอนทิตีและ value object รับผิดชอบ logic ธุรกิจหลักพื้นฐาน ผ่านการแปลง DO และ PO เราสามารถทำให้การคงอยู่ถาวรและการเริ่มต้นข้อมูลสำเร็จ

ออบเจ็กต์หลักของชั้นแอปพลิเคชันคือออบเจ็กต์ DO หากต้องการเรียกใช้บริการแอปพลิเคชันของไมโครเซอร์วิสอื่น DO จะถูกแปลงเป็น DTO ทำให้การประกอบและถ่ายโอนข้อมูลข้ามไมโครเซอร์วิสสำเร็จ ชั้นอินเทอร์เฟซผู้ใช้ทำการแปลง DTO เป็น DO ก่อน จากนั้นบริการแอปพลิเคชันจะรับ DO เพื่อประมวลผลทางธุรกิจ หาก DTO และ DO มีความสัมพันธ์แบบหนึ่งต่อหลาย ในกรณีนี้จำเป็นต้องทำการประกอบข้อมูล DO ใหม่

ชั้นอินเทอร์เฟซผู้ใช้จะทำการแปลง DO และ DTO ซึ่งกันและกัน ทำให้การแลกเปลี่ยนและการแปลงข้อมูลระหว่างไมโครเซอร์วิสกับแอปพลิเคชันส่วนหน้าสำเร็จ บริการ Facade จะประกอบออบเจ็กต์ DO หลายตัว แปลงเป็นออบเจ็กต์ DTO ทำให้การแปลงและถ่ายโอนข้อมูลไปยังแอปพลิเคชันส่วนหน้าสำเร็จ

แอปพลิเคชันส่วนหน้าโดยหลักคือออบเจ็กต์ VO ชั้นแสดงผลใช้ VO ในการแสดงอินเทอร์เฟซ โดยผ่านชั้นอินเทอร์เฟซผู้ใช้และชั้นแอปพลิเคชันใช้ DTO ในการแลกเปลี่ยนข้อมูล

วันนี้เราวิเคราะห์ความสัมพันธ์แบบร่วมมือของบริการและข้อมูลของไมโครเซอร์วิสภายใต้สถาปัตยกรรมแบบแบ่งชั้น DDD เพื่อให้เกิดการลดการเชื่อมโยงระหว่าง aggregate และระหว่างชั้นต่างๆ ของไมโครเซอร์วิส เราได้กำหนดบริการและออบเจ็กต์ข้อมูลที่มีหน้าที่แตกต่างกันในแต่ละชั้น ในกระบวนการพัฒนาซอฟต์แวร์ เราจำเป็นต้องปฏิบัติตามข้อกำหนดด้านหน้าที่ของบริการและข้อมูลในแต่ละชั้นอย่างเคร่งครัด แต่ละฝ่ายอยู่ในตำแหน่งของตนและทำหน้าที่ของตน ด้วยวิธีนี้จึงสามารถรับประกันความเสถียรของโดเมนโมเดลหลัก และในขณะเดียวกันก็สามารถตอบสนองต่อการเปลี่ยนแปลงอย่างรวดเร็วของความต้องการภายนอกได้อย่างยืดหยุ่น
