Subject: A Difficult Technical Decision for a Production Application
1. A Difficult Technical Decision
In the Solar Power Plant Monitoring Dashboard project—an application developed using Go/GORM and running on Docker—there was a scheduler designed to automatically delete logs older than 30 days. One day, it was discovered that the scheduler was failing to complete its tasks (leaving some logs undeleted), and the application container could not resolve hostnames, resulting in errors such as:
text
lookup db on 127.0.0.11:53: no such host
I faced a difficult decision: should I implement an urgent fix by using IP addresses instead of hostnames, or should I address the root cause by properly restructuring the Docker network and DNS configuration from the ground up?
This decision was challenging because the system was already in production; an incorrect fix could impact customers and cause service downtime, yet a quick workaround might lead to recurring issues in the future.
Ultimately, I chose to address the root cause by modifying the `docker-compose.yml` file to include specific DNS settings and clearly separating the network into internal and external segments.

2. Options Considered and Rationale for the Chosen Approach
I considered the following primary options:
Using IP addresses instead of hostnames
Pros: Fast, minimal changes, immediate resolution.
Cons: Unsustainable; if the IP changes, the system breaks again; violates 12-Factor App principles.
Restarting the container
Pros: Simple, no configuration changes required.
Cons: Temporary fix; the problem is likely to recur.
Resetting Docker Desktop
Pros: Might permanently resolve the issue.
Cons: Affects all containers, carries a high risk of downtime, and is not the correct solution.
Adjusting Docker Compose: Adding DNS settings and separating networks
Pros: Addresses the root cause, ensures long-term system stability, and minimizes recurrence.
Cons: Requires more time for testing. Care was also taken to ensure no impact on other containers.
Method 4 was chosen because this is a production system actively used by customers; addressing the root cause helps minimize future incidents and establishes clear network/DNS standards for the team.

2.1 Accepted Risk
The accepted risk was that the network adjustment and container restart might cause brief downtime (approximately 1–2 minutes), potentially causing the scheduler to miss a single execution cycle.
I assessed that this would be acceptable to customers provided there was advance notice and a rollback plan in place. Consequently, I backed up the original configuration and conducted testing in the UAT environment before deploying to production.

3. Testing and Monitoring Procedures
Testing
Test in UAT by simulating a DNS failure scenario.
Verify that the container can resolve the hostname using these commands:

bash
docker exec -it app getent hosts db
docker exec -it app cat /etc/resolv.conf
Run the scheduler to delete logs older than 30 days and verify complete deletion.
Test via Canary Deployment, container by container.

Monitoring

Monitor application and scheduler logs.
Verify the number of deleted logs against expectations.
Monitor queue depth, error rates, and DNS resolution.
Set up alerts for scheduler failures or container DNS resolution issues.
Use SQL commands to check for remaining old logs:

sql
SELECT COUNT(*)
FROM logs
WHERE created_at < NOW() - INTERVAL '30 days';
A result of 0 indicates complete deletion.

4. Post-Deployment Results
After the fix was deployed to production:
Containers could resolve hostnames reliably.
The scheduler successfully completed every execution cycle.
The system successfully deleted all logs older than 30 days, leaving no residual data.
Incidents caused by container-internal DNS issues were significantly reduced. The team established DNS configuration standards and network segmentation within the Compose file.
Features such as health checks, alerts, batch deletion, retries, timeouts, and log deletion checkpoints were implemented.
Customer confidence increased due to the system's genuine automation capabilities.
The time the team spent on manual maintenance and troubleshooting was reduced.

Key Lesson:
While a workaround might offer a quick fix, it is not sustainable for a production environment. Addressing the root cause—despite taking more time—mitigates long-term issues and enhances system reliability.

I am a **Tech Lead / Engineering Lead** managing a **7-person team** (4 Backend, 1 Frontend, 1 QA, and 1 DevOps/Support). One of the engineers is a **Mid-level Backend Engineer** with about two years of experience.

**The Situation**
A solar power plant client repeatedly reported issues where the dashboard displayed data with a lag and the alert system failed intermittently. This engineer handled the tasks merely as tickets, applying quick fixes—such as restarting services or clearing caches—and closing the tickets without analyzing long-term implications. Consequently, the client continued to face the same recurring problems.

**The Responsibility I Assigned**
I shifted his role to become the **End-to-End Owner of the Monitoring & Alerting domain**. He became responsible for the entire pipeline: data ingestion from IoT sensors, processing, dashboard visualization, alerting, and direct communication with the client.
It was no longer just about closing tickets; he had to be able to answer:
- What is the actual problem the client is facing?
- What is the root cause?
- How can we prevent it from happening again?
- How can we assure the client that the issue won't recur?

**Guidance and Performance Review Methods**
- **Weekly 1:1s:** Discussing client issues rather than just ticket progress.
- **Pair RCA:** Conducting Root Cause Analysis together instead of simply issuing orders.
- **Customer Shadowing:** Having him listen directly to the client's feedback to understand the real-world impact.
- **Postmortem Ownership:** Assigning him responsibility for writing the RCA, action items, and preventive actions.
- **Outcome-based Evaluation:** Focusing not on the number of tickets closed, but on:
- Whether the recurrence rate of issues has decreased.
- Whether client satisfaction has improved.
- The effectiveness of monitoring and alerting. ...effectively prevent the issue?
- Are there documents and runbooks available for the team to use?
- **Provide immediate feedback**—both positive and constructive—emphasizing that taking ownership of issues is a crucial skill for senior engineers.

**Transformational Results**
- Tickets related to dashboard delays and malfunctioning alerts **dropped by approximately 60%** within two months.
- The engineer began **proactively questioning** how customers might be affected, rather than simply waiting for tickets to arrive.
- He **initiated the addition of health checks, alerts, and batch retry mechanisms** to the system without needing to be told.
- He **led post-mortem analyses and communicated directly with customers**, thereby increasing customer confidence.
- The team adopted an **ownership model** where each individual had a clearly defined domain of responsibility, moving beyond the mindset of merely closing tickets.
- Customers reported fewer issues, and the after-sales support team found their work easier thanks to clear documentation and alert systems.

**Key Takeaway**
Transforming an engineer from a mere ticket-closer into someone who takes ownership of customer issues requires **clear responsibilities**, **guidance that helps them visualize the impact**, and **performance metrics focused on customer value** rather than just the volume of completed tasks.
