# เล่ม 5: การกำกับดูแลและการปฏิบัติตามข้อกำหนด (Governance & Compliance)

## บทนำ

### คืออะไร
คู่มือเล่มนี้ว่าด้วย **ชั้นการกำกับดูแล** ที่ทำให้ระบบการเงิน-บัญชี (เล่ม 1), กลไกความน่าเชื่อถือ (เล่ม 2), การตรวจสอบย้อนกลับ (เล่ม 3) และสถาปัตยกรรมข้อมูล (เล่ม 4) ไม่เพียงแต่ "ทำงานได้" แต่ยัง **"ปฏิบัติตามข้อกำหนดได้อย่างพิสูจน์ได้"** ครอบคลุมกรอบการกำกับดูแล (COSO, ISO High-Level Structure), การบริหารความเสี่ยง, การรวมศูนย์การควบคุม (Unified Control Library), การกำหนด KPI/SMART สำหรับการกำกับดูแล และการเตรียมพร้อมสำหรับการตรวจสอบจากภายนอก

### คำนำ
องค์กรส่วนใหญ่ไม่ได้ล้มเหลวเพราะขาดการควบคุม แต่ล้มเหลวเพราะ **มีการควบคุมที่กระจัดกระจาย ซ้ำซ้อน และพิสูจน์ไม่ได้**  เมื่อต้องปฏิบัติตามหลายมาตรฐาน (ISO 27001, SOC 2, PCI DSS, COSO, NIST CSF) พร้อมกัน องค์กรที่แยกโปรแกรมการปฏิบัติตามข้อกำหนดออกจากกันจะประสบกับ "ความเหนื่อยล้าจากการตรวจสอบ" (audit fatigue) และใช้ทรัพยากรไปกับการ "พิสูจน์" มากกว่าการปรับปรุง เล่มนี้จึงเสนอแนวทาง **Integrated Management System (IMS)** ที่รวมทุกอย่างไว้ในโครงสร้างเดียว โดยมีการควบคุมเป็น "ความจริงเดียว" (single source of truth) และการบริหารความเสี่ยงเป็นภาษากลาง

### วัตถุประสงค์
1. อธิบายหลักการของ Integrated Management System (IMS) และโครงสร้างแกนกลาง (ISO High-Level Structure)
2. อธิบายการสร้าง Unified Control Library (UCL) ที่รองรับหลายมาตรฐานพร้อมกัน
3. อธิบายการบริหารความเสี่ยงเช่นภาษากลาง (ISO 31000, COSO ERM)
4. อธิบายการออกแบบ evidence repository เดียวสำหรับการตรวจสอบ
5. อธิบาย KPI/SMART สำหรับวัดคุณภาพของการกำกับดูแล
6. ยกตัวอย่างกรณีศึกษา 3–5 กรณี รวมถึงค้าส่ง/ค้าปลีก/POS

### เป้าหมาย
ผู้อ่านสามารถ **ออกแบบระบบกำกับดูแลที่รวมศูนย์** ลดความซ้ำซ้อนในการปฏิบัติตามข้อกำหนด และเตรียมความพร้อมสำหรับการตรวจสอบจากภายนอกได้อย่างมั่นใจ

### ความรู้พื้นฐาน
- Audit และ Audit Log (เล่ม 3)
- Transaction cycles และ assertions (เล่ม 3)
- COSO Internal Control Framework (เล่ม 3)
- KPI/SMART (เล่ม 4)

## บทนิยาม

### 1. Integrated Management System (IMS)

**คืออะไร:** ระบบการจัดการแบบรวมศูนย์ที่นำมาตรฐานหลายฉบับ (ISO 9001, ISO 27001, ISO 22301, SOC 2, PCI DSS, NIST CSF, COSO ฯลฯ) มาหลอมรวมไว้ใน **โครงสร้างเดียว** โดยมีการควบคุม หลักฐาน และกระบวนการตรวจสอบร่วมกัน 

**ทำไมต้องเป็นแบบนี้:** องค์กรที่แยกโปรแกรมต่อมาตรฐานจะเผชิญกับ:
- การเก็บหลักฐานซ้ำซ้อน
- กระบวนการขัดแย้งกัน
- ผู้รับผิดชอบหลายคนสำหรับกิจกรรมเดียวกัน
- คำตอบในการตรวจสอบไม่สอดคล้องกัน 

**เพื่ออะไร / ประโยชน์:**
- ลดต้นทุนและเวลาของการปฏิบัติตามข้อกำหนด
- การควบคุมหนึ่งรายการสามารถตอบสนองหลายมาตรฐาน (เช่น MFA ควบคุมเดียวตอบสนอง ISO 27001, PCI DSS, SOC 2, NIST CSF ได้ 8+ กรอบ) 
- การตรวจสอบกลายเป็น "ผลพลอยได้จากการจัดการที่ดี" ไม่ใช่ "การเตรียมตัวครั้งใหญ่"

**กลุ่มเป้าหมาย:** CISO, ผู้จัดการฝ่ายปฏิบัติตามข้อกำหนด, ผู้ตรวจสอบภายใน, ผู้บริหาร

**Insight:** IMS ไม่ใช่การ "เพิ่มมาตรฐาน" แต่คือการ **"เปลี่ยนมุมมองจากการจัดการกรอบมาตรฐานมาเป็นการจัดการการควบคุม"** 

---

### 2. Unified Control Library (UCL)

**คืออะไร:** รายการหลักของการควบคุมที่องค์กร **ดำเนินการจริง** โดยแต่ละรายการมี ID, วัตถุประสงค์, เจ้าของ, ความถี่, หลักฐานที่ต้องการ, วิธีการดำเนินการ (manual/automated/hybrid), ความเสี่ยงที่เชื่อมโยง และการแมปไปยังกรอบมาตรฐานต่างๆ 

**ทำไมต้องเป็นแบบนี้:** เพื่อให้การควบคุมแต่ละรายการเป็น "ความจริงเดียว" ที่สามารถนำไปใช้ซ้ำในการตรวจสอบหลายครั้ง แทนที่จะสร้างการควบคุมแยกสำหรับแต่ละมาตรฐาน

**ตัวอย่างการแมป:**

| การควบคุม | ตอบสนองกรอบมาตรฐาน |
|---|---|
| **MFA Enforcement** | ISO 27001 Annex A, PCI DSS, SOC 2, NIST CSF, COBIT  |
| **Access Review รายไตรมาส** | ISO 27001, SOC 2, SOX ITGC |
| **Change Management ที่มี Approval Chain** | SOX ITGC, ISO 27001, COBIT |

**เพื่ออะไร:** ทำให้การควบคุมหนึ่งรายการ "ทำงาน" กับหลายมาตรฐานพร้อมกัน ลดความซ้ำซ้อนและความเหนื่อยล้าในการตรวจสอบ

---

### 3. Risk as Common Language

**คืออะไร:** การใช้การบริหารความเสี่ยงเป็น **รากฐานร่วม** ที่ทำให้มาตรฐานต่างๆ สามารถเชื่อมโยงกันได้ แทนที่จะแยกวิเคราะห์ความเสี่ยงต่อมาตรฐาน 

**กรอบที่เกี่ยวข้อง:**
- **ISO 31000:** หลักการบริหารความเสี่ยงโดยรวม
- **COSO ERM:** การกำกับดูแลความเสี่ยงระดับองค์กร
- **ISO 27005 / NIST:** รายละเอียดความเสี่ยงด้านไซเบอร์
- **ISO 22301:** การวิเคราะห์ผลกระทบต่อธุรกิจ (BIA)

**ทำไมต้องเป็นแบบนี้:** เมื่อความเสี่ยงเป็นตัวขับเคลื่อนการตัดสินใจ การควบคุมจะไม่ใช่ "เช็คบ็อกซ์" แต่เป็น "กลไกปกป้องธุรกิจ" 

---

### 4. Evidence Repository เดียว

**คืออะไร:** โครงสร้างโฟลเดอร์/ระบบเดียวที่เก็บหลักฐานทั้งหมดที่ต้องการสำหรับการตรวจสอบ โดยแต่ละการควบคุมชี้ไปยังหลักฐานในที่เดียวกัน 

**โครงสร้างตัวอย่าง:**
```
📁 Access Management
📁 HR Security
📁 Vendor Management
📁 Change Management
📁 Incident Management
📁 Backup & DR Testing
📁 Monitoring & Logs
📁 Awareness & Training
📁 Vulnerability Management
```

**ทำไมต้องเป็นแบบนี้:** การตรวจสอบล้มเหลวไม่ใช่เพราะไม่มีการควบคุม แต่เพราะหลักฐานกระจัดกระจาย หายไป หรือไม่สอดคล้องกัน  การมี repository เดียวeliminates "การล่าหลักฐานแบบตื่นตระหนก" ก่อนการตรวจสอบ

**Insight:** สัญญาณของ IMS ที่成熟คือ: **ถ้าคุณสามารถตอบคำถามผู้ตรวจสอบ ISO และผู้ตรวจสอบ SOC ด้วยชุดหลักฐานเดียวกันได้ แสดงว่าคุณทำถูกต้อง** 

---

### 5. KPI/SMART สำหรับการกำกับดูแล

**คืออะไร:** ตัวชี้วัดที่วัดทั้ง **คุณภาพของการกำกับดูแล** (เช่น ความครอบคลุมของการควบคุม, เวลาตอบสนองต่อเหตุการณ์) และ **ผลลัพธ์** (เช่น จำนวนข้อบกพร่องที่พบในการตรวจสอบ, เวลาในการปิดข้อบกพร่อง)

**หลัก SMART ที่ประยุกต์ใช้:**

| องค์ประกอบ | ตัวอย่างการกำกับดูแล |
|---|---|
| **S**pecific | "ลดจำนวนข้อบกพร่องระดับสูงที่พบในการตรวจสอบ SOX" |
| **M**easurable | "จาก 12 รายการเหลือ 3 รายการ" |
| **A**chievable | "ภายใน 2 ไตรมาส ด้วยการเพิ่มการตรวจสอบภายใน" |
| **R**elevant | "สอดคล้องกับเป้าหมายการผ่าน SOX 404 โดยไม่มี material weakness" |
| **T**ime-bound | "ภายในสิ้นปีงบประมาณ 2027" |

## หลักการทำงาน (Concept)

### สถาปัตยกรรมการกำกับดูแล 4 ชั้น

```
┌──────────────────────────────────────────────────────────────┐
│  ชั้นที่ 1: Governance Structure                                 │
│  - ISO High-Level Structure (HLS) เป็นแกน                      │
│  - คณะกรรมการกำกับดูแล + เจ้าของการควบคุม                          │
│  - นโยบาย วัตถุประสงค์ และขอบเขต                                  │
└─────────────────────┬────────────────────────────────────────┘
                      ▼
┌──────────────────────────────────────────────────────────────┐
│  ชั้นที่ 2: Risk & Control Layer                                 │
│  - บริหารความเสี่ยง (ISO 31000 / COSO ERM)                        │
│  - Unified Control Library (การควบคุม 1 รายการ → หลายมาตรฐาน)   │
│  - การแมปความเสี่ยง ↔ การควบคุม ↔ กรอบมาตรฐาน                      │
└─────────────────────┬────────────────────────────────────────┘
                      ▼
┌──────────────────────────────────────────────────────────────┐
│  ชั้นที่ 3: Evidence & Audit Layer                               │
│  - Evidence Repository เดียว                                   │
│  - Audit Log (เล่ม 3) + Traceability                           │
│  - การตรวจสอบภายในแบบบูรณาการ                                   │
└─────────────────────┬────────────────────────────────────────┘
                      ▼
┌──────────────────────────────────────────────────────────────┐
│  ชั้นที่ 4: Measurement & Improvement                            │
│  - KPI/SMART สำหรับการกำกับดูแล                                  │
│  - การทบทวนโดยผู้บริหาร                                          │
│  - การปรับปรุงอย่างต่อเนื่อง                                          │
└──────────────────────────────────────────────────────────────┘
```

### หลักการสำคัญ 3 ข้อ

**1. โครงสร้างแกนกลางก่อน แล้วจึงเสริมมาตรฐาน**
ใช้ ISO High-Level Structure (Context, Leadership, Planning, Support, Operation, Performance Evaluation, Improvement) เป็น "โครงกระดูก" แล้วเสริม NIST CSF (Identify, Protect, Detect, Respond, Recover) สำหรับมุมมองด้านไซเบอร์ 

**2. การควบคุมสร้างครั้งเดียว แมปหลายครั้ง**
อย่าสร้างการควบคุมสำหรับแต่ละมาตรฐาน แต่สร้างการควบคุม **ครั้งเดียว** แล้วแมปไปยังทุกมาตรฐานที่เกี่ยวข้อง 

**3. หลักฐานคือหลักประกัน ไม่ใช่เอกสาร**
Evidence Repository ต้องถูกออกแบบให้ **"พร้อมสำหรับการตรวจสอบ"** (audit-proof) ตั้งแต่ต้น ไม่ใช่ประกอบขึ้นภายหลัง

## Workflow และ Dataflow (แบบ PSR)

### Problem (ปัญหา)
องค์กรต้องปฏิบัติตามมาตรฐานหลายฉบับ (ISO 27001, SOC 2, PCI DSS, COSO, SOX) แต่:
- มีการเก็บหลักฐานซ้ำซ้อนจากหลายทีม
- การควบคุมเดียวกันถูกประเมินต่างกันในแต่ละมาตรฐาน
- ก่อนการตรวจสอบแต่ละครั้งต้อง "ล่าหลักฐาน" และ "จัดระเบียบใหม่"
- ผู้บริหารไม่เห็นภาพรวมว่าการกำกับดูแลมีประสิทธิผลหรือไม่

### Solution (วิธีแก้)
1. **สร้าง IMS บน ISO HLS:** กำหนดโครงสร้างเดียวที่ทุกมาตรฐานแมปเข้า
2. **สร้าง Unified Control Library:** ระบุการควบคุมที่องค์กรดำเนินการจริง พร้อม mapping ไปยังทุกกรอบ
3. **ใช้ Risk เป็นตัวขับเคลื่อน:** ทุกการควบคุมต้องเชื่อมโยงกับความเสี่ยง
4. **สร้าง Evidence Repository เดียว:** จัดโครงสร้างโฟลเดอร์ตามหมวดหมู่การควบคุม
5. **กำหนด KPI/SMART:** วัดทั้งคุณภาพการควบคุมและผลลัพธ์การตรวจสอบ

### Result (ผลลัพธ์)
- การตรวจสอบ ISO และ SOC ใช้ชุดหลักฐานเดียวกันได้ 
- การควบคุม 1 รายการตอบสนอง 8+ กรอบ ลดความซ้ำซ้อน 
- เวลาเตรียมตัวสำหรับการตรวจสอบลดลงอย่างมีนัยสำคัญ
- ผู้บริหารมีตัวชี้วัดที่ชัดเจนสำหรับการกำกับดูแล

---

## บทสรุป

### ประโยชน์ที่ได้รับ
- เข้าใจหลักการ IMS และโครงสร้าง ISO HLS
- สามารถสร้าง Unified Control Library ที่รองรับหลายมาตรฐาน
- เข้าใจการใช้ Risk เป็นภาษากลางในการเชื่อมโยงมาตรฐาน
- สามารถออกแบบ Evidence Repository เดียวสำหรับการตรวจสอบ
- กำหนด KPI/SMART สำหรับวัดคุณภาพการกำกับดูแล

### ข้อควรระวัง
- **อย่าเริ่มจากมาตรฐาน:** เริ่มจากโครงสร้างแกนกลางและการควบคุมที่มีอยู่จริง แล้วจึงแมปมาตรฐาน 
- **อย่าทำ IMS เป็น "โครงการเอกสาร":** ถ้าการควบคุมไม่ได้ถูกดำเนินการจริง เอกสารก็ไร้ค่า
- **KPI ต้องวัดทั้งมิติคุณภาพและผลลัพธ์:** วัดเฉพาะจำนวนการควบคุมโดยไม่ดูประสิทธิผลจะทำให้เกิด "เช็คบ็อกซ์"
- **Evidence Repository ต้องเข้าถึงได้ง่าย:** ถ้าต้องใช้เวลานานในการหาหลักฐาน แสดงว่าโครงสร้างผิด

### ข้อจำกัด
- IMS ต้องใช้ความร่วมมือจากหลายฝ่าย (IT, Audit, Compliance, Business)
- การแมปมาตรฐานต้องใช้เวลาในช่วงเริ่มต้น (แต่ประหยัดกว่าในระยะยาว)
- เครื่องมืออย่าง SCF (Secure Controls Framework) ช่วยลดเวลาแมปได้ แต่ยังต้องปรับให้เข้ากับบริบทองค์กร 

### ข้อห้าม
- ห้ามสร้างโปรแกรมแยกสำหรับแต่ละมาตรฐานโดยไม่มีการเชื่อมโยง
- ห้ามใช้ shared credentials ในระบบที่มี audit trail (เชื่อมโยงกับเล่ม 3)
- ห้ามกำหนด KPI ที่วัดไม่ได้หรือไม่มีเจ้าของที่ชัดเจน
- ห้ามถือว่า "ผ่านการตรวจสอบ" คือเป้าหมายสูงสุด — เป้าหมายคือการกำกับดูแลที่มีประสิทธิผล

---

## ตัวอย่างการใช้งานจริง 3–5 กรณี

### กรณีที่ 1: Unified Control Library สำหรับ ISO 27001 + SOC 2 + PCI DSS

**Problem:** องค์กรต้องผ่านการตรวจสอบ 3 มาตรฐาน แต่ละมาตรฐานมีข้อกำหนดที่ดูเหมือนแตกต่างกัน ทำให้ทีมต้องเตรียมเอกสาร 3 ชุด

**Solution:** สร้าง UCL โดยระบุการควบคุมที่มีอยู่แล้วและแมป:

| Control ID | การควบคุม | ISO 27001 | SOC 2 | PCI DSS | เจ้าของ | หลักฐาน |
|---|---|---|---|---|---|---|
| AC-01 | MFA สำหรับการเข้าถึงระบบสำคัญ | A.5.17 | CC6.1 | 8.4 | IT Security | Log การเปิดใช้ MFA |
| CM-02 | Change Management ที่มี Approval | A.8.32 | CC8.1 | 6.5 | IT Ops | Change ticket + approval |
| LG-03 | Logging และ Monitoring | A.8.15 | CC7.2 | 10.x | SOC Team | SIEM dashboard + retention |

**Result:** ทีมเตรียมหลักฐานชุดเดียวที่ตอบสนองทั้ง 3 มาตรฐาน ลดเวลาการเตรียมตัว 60%

---

### กรณีที่ 2: KPI/SMART สำหรับการกำกับดูแล SOX ITGC

**Problem:** องค์กรไม่รู้ว่าการควบคุม ITGC มีประสิทธิผลหรือไม่ จนกระทั่งผู้ตรวจสอบภายนอกพบข้อบกพร่อง

**Solution:** กำหนด KPI ตาม SMART:

| KPI | Specific | Measurable | Achievable | Relevant | Time-bound |
|---|---|---|---|---|---|
| อัตราการผ่าน ITGC | การควบคุม 4 ด้าน (change, access, audit trail, development) | ≥ 95% ผ่าน | ปรับปรุงจาก 78% | ผ่าน SOX 404 | ก่อนการตรวจสอบ Q4 |
| เวลาปิดข้อบกพร่อง | ข้อบกพร่องระดับสูง | ≤ 30 วัน | เพิ่มทรัพยากร | ลด material weakness | ทันที |
| ความครอบคลุมของ Audit Trail | ตารางทางการเงิน | 100% มี audit log | เพิ่ม trigger | SOX/PCAOB | 1 ไตรมาส |

**Result:** ทีมมีเป้าหมายชัดเจน ผู้บริหารติดตามได้ทุกเดือน และผ่านการตรวจสอบโดยไม่มี material weakness

---

### กรณีที่ 3: Evidence Repository สำหรับค้าปลีก/POS (เชื่อมโยงกับเล่ม 4)

**Problem:** ร้านค้าปลีกมีหลายสาขา แต่ละสาขาเก็บหลักฐานการปิดกะ (cash reconciliation) ต่างกัน ทำให้การตรวจสอบภายในยุ่งยาก

**Solution:** สร้าง Evidence Repository ส่วนกลางที่แต่ละสาขาอัปโหลด:
- รายงานการปิดกะ POS (พร้อม timestamp และผู้ปิด)
- หลักฐานการกระทบยอดเงินสด (ถ้ามีส่วนต่าง ต้องมีผู้อนุมัติ)
- Audit log ของการแก้ไขราคา/ส่วนลด 

**KPI ที่เกี่ยวข้อง:**
- "สาขาที่ปิดกะภายในวันเดียวกัน: ≥ 98%" (ตามข้อกำหนดว่าการปิดกะ POS ต้องเสร็จภายในวันเดียวกัน )
- "ส่วนต่างเงินสดที่ได้รับการอนุมัติ: 100%"

**Result:** การตรวจสอบภายในสามารถดูหลักฐานจากส่วนกลางได้ ลดเวลาในการตรวจสอบแต่ละสาขา

---

### กรณีที่ 4: การใช้ Risk เป็นตัวขับเคลื่อนสำหรับการควบคุม Access

**Problem:** องค์กรมีการควบคุม Access หลายรายการ แต่ไม่รู้ว่าอันไหนสำคัญที่สุด

**Solution:** ทำ risk assessment โดยระบุ:
- **ความเสี่ยง:** การเข้าถึงข้อมูลลูกค้าที่ไม่ได้รับอนุญาต → ข้อมูลรั่วไหล → ค่าปรับ GDPR/PDPA
- **การควบคุมที่เชื่อมโยง:** MFA, Access Review รายไตรมาส, Least Privilege, Logging
- **การแมป:** การควบคุมเหล่านี้ตอบสนอง ISO 27001, SOC 2, PCI DSS

**Result:** องค์กรสามารถจัดลำดับความสำคัญของการควบคุมตามความเสี่ยง และสื่อสารกับผู้บริหารได้ว่า "ทำไมต้องลงทุนในการควบคุมนี้"

---

### กรณีที่ 5: การเตรียมพร้อมสำหรับการตรวจสอบ SOX ด้วย IMS

**Problem:** ผู้ตรวจสอบ SOX ถามว่า "แสดงการเปลี่ยนแปลงทั้งหมดในระบบรายงานทางการเงิน 12 เดือนที่ผ่านมา ใครอนุมัติ และเพราะอะไร" (เชื่อมโยงกับเล่ม 3)

**Solution:** ใช้ Evidence Repository ที่มี:
- Change tickets พร้อม approval chain (บันทึกในระบบ ไม่ใช่ screenshot จาก chat)
- Audit log ของการ execute (พร้อม SQL statement, who, when, approval) 
- Business justification ที่เชื่อมโยงกับ ticket

**Result:** สามารถ export หลักฐาน 12–18 เดือนที่ต่อเนื่องได้ทันที และผ่านข้อกำหนด ITGC

---

## การใช้งาน

### หลักการนำไปใช้
1. **เริ่มจากสิ่งที่มีอยู่:** สำรวจการควบคุมที่องค์กรดำเนินการจริงก่อนสร้าง UCL
2. **เลือกโครงสร้างแกนกลาง:** ใช้ ISO HLS เป็นโครงกระดูก แล้วเสริม NIST CSF สำหรับมุมมองปฏิบัติการ
3. **แมปมาตรฐานเข้ากับการควบคุม:** ไม่ใช่สร้างการควบคุมใหม่ต่อมาตรฐาน
4. **ใช้ Risk เป็นตัวขับเคลื่อน:** ทุกการควบคุมต้องมี "ทำไม" ที่ชัดเจน
5. **สร้าง Evidence Repository เดียว:** โครงสร้างต้องทำให้ "หาหลักฐานได้ในไม่กี่วินาที"
6. **กำหนด KPI/SMART:** วัดทั้งคุณภาพและผลลัพธ์ ติดตามทุกไตรมาส
